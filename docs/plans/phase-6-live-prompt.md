# Phase 6 — Live prompt: one concept at a time

Request: the student page shows **one** card — the instructor's current concept — instead of all five, and a student can only rate concepts the instructor has actually made current in this session. When the instructor changes the current concept every student's card switches live. The instructor sees how many participants have answered the current prompt.

## Plan

- **Schema.** `sessions.activeHistory?: { conceptId, at }[]` — every concept that has been made current in this session, in the order it first became current. `sessions.create` seeds it with the first concept (which it already makes current); `sessions.setActiveConcept` (`{ sessionId, instructorSecret, conceptId, question? }`) appends a concept the first time it becomes current and never twice; for a session created before this field existed it first records the concept that was current. `sessions.activePrompt?: string` — the optional one-line question pushed with the current concept: `question` is trimmed, must be ≤ 200 chars (`ConvexError` otherwise), and is cleared whenever a concept is made current without text (so the plain *Make current topic* button clears it). `seed.reset` marks all five concepts as covered (history order 0→4, *Call stack & frames* current) so the 106 seeded `pre` signals stay valid.
- **Server gate.** `signals.upsert` (the session-page rating, always `pre`) accepts a concept only if it is the current concept or appears in `activeHistory`; otherwise `ConvexError("That concept hasn't been covered yet")`. `signals.roomCheckIn` (the `post` path for room members) is untouched — a room is always about a published cluster's concept and is the only after-help input.
- **Student query.** `sessions.getStudentView` returns, in addition to the existing fields, `coveredConceptIds` — previously-active concept ids in history order, excluding the current one. `concepts[]` keeps `myLevel` for every concept (never aggregates); all concepts are still returned because the question box, published clusters, helper opt-in and room list can be about any concept.
- **Student UI (`StudentCockpit`).** One indigo "Current topic" card: headline **Prompt N of 5** (N = the concept's position in the instructor's concept list), label, description, the pushed question (if any) in a white box, the three `min-h-14` confidence buttons. When the prompt (concept or pushed question) changes while the page is open a "New prompt" badge shows for ~3 s (keyed to the new prompt so it can never describe a stale one). Below it a collapsed native `<details>` **Already covered (n)** list with the student's own answer per covered concept, editable so they can revise after help. Concepts never made current are not rendered. No current concept → a "Waiting for the first prompt" card. Layout stays ≤ 400 px friendly (`max-w-xl`, `p-3`).
- **Instructor query/UI.** `sessions.getInstructorView` gains `answeredCount` (participants with a `pre` signal on the current concept — one signal per participant and concept, so it is the concept's `total`), `coveredConceptIds` and `activePrompt`; no existing field is renamed or removed. `RadarDashboard` adds a fifth metric card **Participation**: `answered / joined` with a percentage, `incl. n simulated` when simulated participants exist (they join and are seeded with answers). The per-concept list marks covered concepts with `covered · N answered` and never-active ones with `not yet covered`. Under the header a **Push prompt** form (concept select defaulting to the current concept, optional ≤ 200-char question, button) calls the same `setActiveConcept`; the existing *Make current topic* button in the concept details stays. A TA uses the same instructor URL + secret — there are no separate roles.
- **Tests.** `signals.test.ts`: upsert rejected for a never-active concept, accepted for the current one and for a previously-active one; `answeredCount`/`participantCount` track answers live; `setActiveConcept` appends to `activeHistory` once per concept (and keeps the pre-upgrade current concept covered), stores a trimmed `activePrompt`, clears it when the question is omitted and rejects > 200 chars; `getStudentView` exposes `coveredConceptIds` and no counts. Scenario 9 now makes its concept current first. `seed.test.ts` checks the seeded history and that a real student can rate a non-current seeded concept.

## Decisions (simplest option, documented here)

- "Prompt N of 5" uses the concept's order in the session's concept list, not the position in `activeHistory`, so the number is stable when the instructor goes back to a concept.
- Covered concepts are listed in the order they first became current; the current one is excluded from that list.
- Re-selecting the current concept is a no-op for `activeHistory` and for the "New prompt" cue.
- The Lecture Listener (session G) was cancelled; the manual *Push prompt* form replaces it. Pushing the current concept again with a new question only changes the question (history unchanged) and still triggers the student "New prompt" cue. Ratings stay per concept (one signal per participant and concept — no prompt revision on signals, which would be another schema change), so Participation and the students' selected levels carry over when only the question changes; the Push prompt form says so.
- `answeredCount` counts `pre` signals only, like the rest of the dashboard; simulated participants count toward both sides of the ratio and are labelled.

## Acceptance

`npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build` clean. Live on the shared dev deployment: student (390 px) sees one card; instructor presses *Make current topic* on another concept → the student's card switches without a refresh and shows *New prompt*; the instructor pushes a question with *Push prompt* → it appears under the description on the student card; the student answers → *Participation* increments; the student revises a concept under *Already covered*; a never-active concept is not shown and `signals.upsert` for it is rejected.
